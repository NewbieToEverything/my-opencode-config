# 下载速率诊断

> 按需加载：下载卡住、或速率低于 50 kb/s 时读本文档。正常构建不涉及本内容。
> 实测环境：Linux / Docker + nvidia-container-toolkit / RTX 5070 Ti 16GB（sm_120）/ hf-mirror.com。带具体速率的结论以此环境为准，跨机器需重新实测。

## 核心认知

50 kb/s 这个阈值只告诉你"该收手"，不告诉你**为什么慢**。绝大多数"下载很慢"不是网络带宽不足，而是**上游按连接限速**——此时换镜像源、改 daemon 代理都无效，**只有增加并发连接才有效**。

实测现象：Docker Hub 与 hf-mirror.com 均为「单连接 30 秒内约 9 MB/s，随后掉到 180 KB/s」。同一时刻开 3~4 条新连接，总吞吐立刻从 2 MB/s 升到 13 MB/s。同一个文件、同一个代理、同一时刻。

## 动手前先测三件事

### 1. 当前真实速率

不要只看点对点的估计，用网卡计数器：

```bash
A=$(awk '/:/{s+=$2} END{print s}' /proc/net/dev); sleep 10
B=$(awk '/:/{s+=$2} END{print s}' /proc/net/dev); echo $(( (B-A)/1024/10 )) KB/s
```

### 2. 代理是否已经配置

避免把时间花在重复配置上：

```bash
docker info | grep -i "proxy"
systemctl show docker --property=Environment | tr ' ' '\n' | grep -i proxy
```

**`systemctl show` 的 `Environment` 不展开 `EnvironmentFile`**——drop-in 里写的是 `EnvironmentFile=/etc/default/proxy.conf` 时，这条命令会显示为空，让人误判"没配代理"。此时以 `docker info` 为准。

### 3. 是按连接限速，还是总带宽上限

取大文件中段做 range 请求测速（如 `-r 600000000-620971519`），与一条长连接的持续速率对比：

| 长连接持续速率 | 短请求速率 | 结论 |
|---------------|-----------|------|
| 远低于短请求 | 短请求很快 | **按连接限速** → 加并发 |
| 与短请求相当 | 两者都慢 | 总带宽上限 → 只能等 |

## 确认按连接限速后的处理（按代价从低到高）

1. **换并发**：用多个独立连接分块拉取同一文件，每块一次新的 HTTP range 请求。实测 8~12 路并发可拿 4~6 倍。
2. **预先放好文件**：容器内程序自带的单连接下载改不了并发时，改成把文件提前放进数据目录（用**原始文件名**）。多数项目支持检测到文件后跳过下载，正确性由程序自己的 sha256 校验兜底。先看它的日志里是否打印了类似"Files you already have: put them here with their original names"的提示。
3. **用过滤参数拆并行**：上游程序若有 `--only` / 分片 / 分页之类的过滤参数，用它把工作拆成互不冲突的子集并行；收尾再跑一次**不带过滤**的全量命令，让它写完整清单并做校验。注意并行实例会争抢同一个输出文件——确认各自写不同文件，否则先停掉串行实例。
4. **在宿主机直接跑下载脚本**：容器内程序不支持并行时，若它的下载脚本只依赖标准库、且校验表硬编码在源码里，宿主机 `python3` 即可执行，无需进容器。

## 不要做的事

- **不要因为慢就去改 daemon 代理**——先确认代理是否已经配好、瓶颈是否在代理节点本身。
- **不要只取大文件头部测速**：`curl -r 0-20971519` 取的是开头区间，常命中 CDN 缓存，速率虚高数倍。取中段才接近真实持续吞吐。
- **不要把"并行无效"的结论建立在只测量了单方流量的实验上**。并行实验必须用 `/proc/net/dev` 量**总**吞吐；只量其中一个下载者的落盘量，会把它的**份额**当成总量，得出"并行反而更慢"的错误结论。这是本项目实测踩过的坑。

## 断点续传

长时间下载一律要求可续传：分块落到 parts 目录、逐块记录完成状态。这样重启、并行改造、被中断都能接着走，避免重下几十 GB。续传改造也顺带避免了并行时新旧进程抢同一文件的问题——先杀掉串行进程，再确认它打开的文件描述符指向的是已被替换的旧 inode（`ls -l /proc/<pid>/fd | grep <文件名>` 会显示 `(deleted)`），才可安全启动并行下载。

## 已落地的参考实现

`~/.cache/strata-tools/` 下有三个本次实战产出、可直接复用的脚本：

| 脚本 | 用途 |
|------|------|
| `dl-iq3s.py` | 分块并行下载 + 逐文件 sha256 校验 + 断点续传 |
| `fast-gate-up.py` | 已知字节范围时，直接多路并发拉取单个超大对象 |
| `mtp-parallel.sh` | 上游工具只有 `--only` 过滤时，用它拆子集并行 + 收尾全量校验 |

关键设计：所有目标文件都是**内容寻址**的（OCI blob 按 digest、HF 张量按 LFS sha256），逐个校验通过才会装配或改名，任何一个字节不符即中止——这样并行下载与换源不会引入静默损坏。
